@@I What are DevTools?
**Flutter DevTools** is a set of **debugging and performance tools** for Flutter and Dart apps. It opens in the browser or inside VS Code / Android Studio while the app runs in debug mode.

- **Flutter Inspector** – see and explore the widget tree
- **Performance view** – find slow (janky) frames
- **CPU Profiler** and **Memory view** – find heavy code and memory leaks
- **Network view** – check HTTP requests
- **Debugger** and **Logging** view

@@I What is InheritedWidget?
`InheritedWidget` is a special widget that **passes data down the widget tree**. Any widget below it can read that data directly through `context`, without passing it through every constructor. When the data changes, only the widgets that use it are rebuilt.

```dart
class UserInfo extends InheritedWidget {
  final String name;
  const UserInfo({super.key, required this.name, required super.child});

  static UserInfo of(BuildContext context) =>
      context.dependOnInheritedWidgetOfExactType<UserInfo>()!;

  @override
  bool updateShouldNotify(UserInfo old) => name != old.name;
}
// Any child can now use: Text(UserInfo.of(context).name)
```

`Theme.of(context)` and `MediaQuery.of(context)` work this way, and the Provider package is built on it.

@@I Explain Stream-based state management with RxDart.
A **Stream** is a flow of values over time, like water through a pipe. The UI listens to a stream with **`StreamBuilder`** and rebuilds whenever a new value arrives. **RxDart** is a package that adds extra power to Dart streams:

- **Subjects** – a stream we can push values into. `BehaviorSubject` remembers the **latest value** and gives it to every new listener; `PublishSubject` sends only new values; `ReplaySubject` replays all old values.
- **Operators** – tools such as `map`, `where`, `distinct`, `debounceTime` (wait until the user stops typing) and `combineLatest`.

**Flow:** the UI calls a method → the logic class adds a value to the subject → `StreamBuilder` receives it → the UI rebuilds.

```dart
import 'package:rxdart/rxdart.dart';

class CounterBloc {
  final _count = BehaviorSubject<int>.seeded(0);   // starts at 0
  Stream<int> get count => _count.stream;

  void increment() => _count.add(_count.value + 1);
  void dispose() => _count.close();
}
```

```dart
StreamBuilder<int>(
  stream: bloc.count,
  builder: (context, snapshot) => Text('Count: ${snapshot.data ?? 0}'),
)
// Button: ElevatedButton(onPressed: bloc.increment, child: Text('+'))
```

The logic stays outside the widgets, so it is easy to test and reuse.

@@I Write a note on ScopedModel.
**ScopedModel** (`scoped_model` package) is a simple way to **share data with many widgets** and rebuild them when the data changes. It has three main parts:

- **`Model`** – our data class extends `Model` and calls **`notifyListeners()`** whenever the data changes.
- **`ScopedModel<T>`** – wraps a part of the widget tree and **provides** the model to it.
- **`ScopedModelDescendant<T>`** – any widget below that **uses** the model. Its builder runs again when `notifyListeners()` is called.

```dart
class CounterModel extends Model {
  int count = 0;
  void increment() {
    count++;
    notifyListeners();            // tell listening widgets to rebuild
  }
}

ScopedModel<CounterModel>(
  model: CounterModel(),
  child: ScopedModelDescendant<CounterModel>(
    builder: (context, child, model) => TextButton(
      onPressed: model.increment,
      child: Text('Count: ${model.count}'),
    ),
  ),
)
```

ScopedModel is easy to learn, but it is an older package. Today **Provider**, which works in a very similar way, is the recommended choice.

#### How it works

1. The user taps a button, so the UI **adds an event** (for example `Increment`) to the BLoC.
2. The BLoC runs the **logic** (calculation, API call, database work).
3. The BLoC **emits a new state** (for example `count = 5`).
4. Widgets listening to the BLoC **rebuild** with the new state.

#### Main classes of the `flutter_bloc` package

- **`Bloc` / `Cubit`** – hold the logic (`Cubit` is a simpler BLoC that uses methods instead of events).
- **`BlocProvider`** – gives the BLoC to the widget tree.
- **`BlocBuilder`** – rebuilds the UI when the state changes.
- **`BlocListener`** – does one-time actions such as showing a SnackBar or navigating.

#### Example: counter

```dart
abstract class CounterEvent {}
class Increment extends CounterEvent {}
class Decrement extends CounterEvent {}

class CounterBloc extends Bloc<CounterEvent, int> {
  CounterBloc() : super(0) {                       // starting state = 0
    on<Increment>((event, emit) => emit(state + 1));
    on<Decrement>((event, emit) => emit(state - 1));
  }
}
```

```dart
BlocProvider(
  create: (_) => CounterBloc(),
  child: Builder(
    builder: (context) => Scaffold(
      body: Center(
        child: BlocBuilder<CounterBloc, int>(
          builder: (context, count) => Text('$count', style: const TextStyle(fontSize: 40)),
        ),
      ),
      floatingActionButton: FloatingActionButton(
        onPressed: () => context.read<CounterBloc>().add(Increment()),
        child: const Icon(Icons.add),
      ),
    ),
  ),
)
```

#### Advantages

- UI and logic are separate, so the code is clean and easy to test.
- State changes are predictable: one event in, one state out.
- The same BLoC can be reused on different screens.

The only drawback is some extra code (events and states classes), which is worth it for medium and large apps.

@@I Explain Redux architecture for Flutter.
**Redux** is a state management pattern (first made for JavaScript) that keeps the **whole app state in one place, called the store**, and allows data to flow in **only one direction**. In Flutter we use it with the `redux` and `flutter_redux` packages.

#### Main parts

- **Store** – one object that holds the complete app state (single source of truth).
- **State** – the data; it is never changed directly.
- **Action** – a simple object that says **what happened**, like `IncrementAction`.
- **Reducer** – a **pure function** `(oldState, action) => newState` that creates the new state.
- **Middleware** (optional) – runs between the action and the reducer, for API calls or logging.

#### Example: counter with flutter_redux

```dart
enum CounterAction { increment }

int counterReducer(int state, dynamic action) {   // pure function
  if (action == CounterAction.increment) return state + 1;
  return state;
}

void main() {
  final store = Store<int>(counterReducer, initialState: 0);

  runApp(StoreProvider<int>(
    store: store,
    child: MaterialApp(
      home: Scaffold(
        body: Center(
          child: StoreConnector<int, String>(
            converter: (store) => store.state.toString(),
            builder: (context, count) => Text(count, style: const TextStyle(fontSize: 40)),
          ),
        ),
        floatingActionButton: FloatingActionButton(
          onPressed: () => store.dispatch(CounterAction.increment),
          child: const Icon(Icons.add),
        ),
      ),
    ),
  ));
}
```

#### Three principles of Redux

1. **Single source of truth** – the whole state is in one store.
2. **State is read-only** – the only way to change it is to dispatch an action.
3. **Changes are made by pure functions** – reducers return a new state without side effects.

**Advantages:** predictable behaviour, easy debugging and testing. **Drawback:** a lot of extra code, so it suits large apps more than small ones.
